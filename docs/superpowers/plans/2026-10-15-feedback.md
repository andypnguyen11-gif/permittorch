# In-app Feedback Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Signed-in users send feedback from a sidebar dialog; the API stores it and emails it to the owner, retrying hourly if the email fails.

**Architecture:** New vertical slice `apps/api/Features/Feedback/` (endpoint, page-path rule, email builder, notifier). The notifier sends through the existing `ResendEmailClient` with idempotency key `feedback:{id}`; `DigestBackgroundService` gains a separately guarded retry step. The web app adds one shared form, a dialog, a sidebar item and an API client function — no business rules on the web side.

**Tech Stack:** ASP.NET Core minimal APIs, EF Core + Npgsql (snake_case naming), xUnit + Testcontainers; Next.js, base-ui shadcn components, Vitest + Testing Library.

**Spec:** `docs/superpowers/specs/2026-10-15-feedback-design.md`

## Global Constraints

- Signed-in only: endpoint uses the existing `"User"` policy. No public page, no footer or login-page link, no landing-page change.
- Any signed-in account may submit, with or without a subscription. No terms or entitlement check on this endpoint.
- Identity only from the login. The request body has no user id or email; unknown JSON fields are ignored.
- Types: `Idea`, `Problem`, `DataRequest`, `Other`. On the wire they follow the project's JSON enum convention (`JsonStringEnumConverter(SnakeCaseUpper)`): `IDEA`, `PROBLEM`, `DATA_REQUEST`, `OTHER`. In the database they follow the project convention of integer enum columns.
- Message: trimmed, 1–5000 characters. Page path: max 500, kept only if it passes `FeedbackPagePath.Normalize`; otherwise stored null and the message is still accepted.
- Rate limit policy `feedback`: fixed window, 5 per 10 minutes, partition `"sub:" + sub`.
- Success response: 202 Accepted, independent of the email outcome.
- Idempotency key: `feedback:{id}`. The email is built only from the saved row and its user; no send-time values.
- Retry: rows with `notified_at IS NULL` and `created_at` older than 5 minutes; separate try/catch from digests; paused when `Digests:Enabled=false`.
- `FEEDBACK_NOTIFY_EMAIL` unset → save, send nothing, log `Feedback {Id} saved but FEEDBACK_NOTIFY_EMAIL is unset` (never the message).
- Logs never include the message text.
- No E2E spec for this feature.
- Commits: imperative subject, no task IDs or PR numbers, no Co-Authored-By or "Generated with" lines (CLAUDE.md).
- Work on branch `feat/in-app-feedback`.

## Review Focus

1. **Org name or account email changes between the first send and a retry.** The rebuilt email differs, so Resend answers 409 for the same key; the row must stay pending (logged, not thrown) and send once the key expires. Pinned in Task 4 (409 leaves row pending, sweep continues to the next row).
2. **`created_at` precision.** The first send uses the in-memory entity (100 ns ticks); the retry reads Postgres (µs). Any timestamp in the email must be formatted to the minute so both builds match. Pinned in Task 3 (sub-microsecond tick difference gives identical output).
3. **Multi-line and very long messages in the subject.** Newlines must collapse to spaces before the 60-character cut, and the cut must not split a surrogate pair. Pinned in Task 3.
4. **Phone menu closes, dialog must survive.** If the dialog lives inside the sheet it unmounts when the sheet closes. Pinned in Task 8 (dialog is still open after the sheet closes).
5. **Double-click submit.** The button is disabled while sending so one click gives one row. Pinned in Task 7.
